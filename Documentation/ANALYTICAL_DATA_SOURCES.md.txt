# Community Health Intelligence Atlas (CHIA)

# Analytical Data Sources

## Purpose

This document records the provenance of the authoritative **analytical** source
artifacts that feed the CHIA v0.1 processing pipeline (CE-A00..CE-A06), so that
every value persisted in `Data/Model/chia_v01.sqlite` can be traced back to an
exact, hash-identified source vintage together with the methodology version that
transformed it.

It is the analytical-layer counterpart to
`Documentation/GEOGRAPHIC_DATA_SOURCES.md.txt`, which covers the separate
presentation/navigation geographic boundary layer (CE-E01). The two layers do
not share data and are versioned independently.

This document is produced by **CE-E12A** (data-vintage design; documentation
only). CE-E12A records these facts; it does **not** modify the database, the
build scripts, the seed SQL, or any application code. Populating the persisted
`source` table with the values below is the separately authorized follow-on
slice **CE-E12B**.

---

# Governing Principle

> A CHIA profile must always be reproducible from a known set of source-data
> vintages and a known methodology version.

Two identifiers, kept deliberately separate, are together sufficient to
reproduce any persisted profile value:

| Identifier | Where it lives | v0.1 value |
| --- | --- | --- |
| **Methodology version** | `methodology.methodology_version`, `normalized_measure.methodology_version`, `dimension_score.methodology_version`, `composite_score.methodology_version`, `dimension_definition.methodology_version` | `v0.1` |
| **Source-data vintage** | `source.reference_period` (+ `source.url`, `source.accessed_at`, and — proposed for CE-E12B — a content hash) | *placeholder today; target values below* |

`county_period.period` is the analytical-run partition key. In v0.1 it is
coupled 1:1 to the methodology version (value `v0.1`) and is asserted `== 'v0.1'`
by `Data/Model/validate_v01_county_explorer.py` and the backend suite. It is
**not** a data-vintage field and CE-E12A/CE-E12B do not change its value.

# Pipeline Position

```
HRSA Data Warehouse full-detail exports         (Data/Raw/, gitignored)
  BCD_HPSA_FCT_DET_PC.csv / _DH.csv / _MH.csv
  MUA_DET.csv
        |
        v   validated spatial-coverage work (pre-CE-A00; area-intersection
        |   against the 2020 county universe, severity/designation rollups)
        v
Validated spatial-coverage workbooks            (Data/Processed/, gitignored)
  CHIA_Primary_Care_HPSA_Spatial_Coverage_Validated_FINAL.xlsx
  CHIA_Dental_HPSA_Spatial_Coverage_Validated_FINAL.xlsx
  CHIA_Mental_Health_HPSA_Spatial_Coverage_Validated_FINAL.xlsx
  CHIA_MUA_P_Spatial_Coverage_Validated.xlsx
        |
        v   Data/Model/build_v01_database.py   (sheet "County Coverage")
        v
observation
        |
        v   Data/Model/normalize_v01_database.py      -> normalized_measure
        v   Data/Model/build_v01_dimension_scores.py  -> dimension_score
        v   Data/Model/build_v01_composite_scores.py  -> composite_score
        v
Data/Model/chia_v01.sqlite  ->  read-only FastAPI  ->  County Explorer UI
```

The four `Data/Processed/*.xlsx` workbooks are the **direct** build inputs
(`build_v01_database.py :: SOURCE_FILES`). The four `Data/Raw/*.csv` files are
their documented upstream (the HRSA exports the spatial-coverage work consumed);
they are recorded here for traceability but are not read by any script in this
repository's `Data/Model/` pipeline.

No script in the analytical pipeline (`normalize_v01_database.py`,
`build_v01_dimension_scores.py`, `build_v01_composite_scores.py`, or any
`validate_v01_*`) reads the `source` table. `source` participates only in the
presentation-layer provenance join
(`app/services/county_explorer.py :: _load_provenance`) and the CE-E11 per-county
CSV export. Populating source-vintage metadata therefore cannot change any
analytical value.

# Source Vintage

All four v0.1 analytical sources are extracts of the **HRSA Data Warehouse**,
taken as a single snapshot. Every record in each raw export carries a uniform
`Data Warehouse Record Create Date` of **2026-08-29** (verified across all rows:
PC 79,358 / DH 46,316 / MH 40,736 / MUA-P 19,778). The local retrieval date
matches the create date.

| Field | Value |
| --- | --- |
| Publisher | U.S. Health Resources & Services Administration (HRSA) |
| Data store | HRSA Data Warehouse |
| Snapshot date | 2026-08-29 (`Data Warehouse Record Create Date`, uniform across all records) |
| Retrieved (`accessed_at`) | 2026-08-29 |
| Canonical download location | `https://data.hrsa.gov/data/download` (HPSA and MUA/P "full detail" CSV exports) |
| License / terms | Public domain (U.S. federal government work) |

## `reference_period` string convention

A single human-readable, sortable string per `source` row, of the form:

```
<data store> snapshot <ISO-8601 date>
```

For every v0.1 `source` row the target value is:

```
HRSA Data Warehouse snapshot 2026-08-29
```

This replaces the current placeholder `v0.1 source period`. `source.url` and
`source.accessed_at` are populated alongside it (both currently `NULL`).

> Open item carried to CE-E12B (Q-D5): the exact deep-link download URL for each
> HRSA full-detail export should be confirmed against the HRSA download portal at
> population time. `https://data.hrsa.gov/data/download` is the verified
> canonical landing location; a more specific per-export URL is not recorded
> in-repo today.

# Known Limitations and Notes

* **CE-E12A is documentation only.** No `.py`, `.sql`, `.sqlite`, frontend, or
  test file is modified. The persisted `source` table still holds the
  `v0.1 source period` placeholder and `NULL` `url` / `accessed_at` until
  CE-E12B is authorized and run.
* **Artifacts are gitignored.** `Data/Raw/` and `Data/Processed/` are not
  committed. This document's recorded hashes are the in-repo identity of record;
  they let a future environment confirm it holds the same source vintage before
  trusting a rebuild.
* **HRSA deep-link URLs** for the individual full-detail exports are not recorded
  in-repo. The verified canonical location is `https://data.hrsa.gov/data/download`.
* **Vintage granularity.** HRSA publishes a continuously updated data warehouse
  rather than discrete numbered releases; the `Data Warehouse Record Create Date`
  (2026-08-29, uniform) is the most precise vintage identifier available and is
  what the `reference_period` convention encodes.
* A future source refresh (a newer HRSA snapshot) is a methodology-version-neutral
  change to source vintage; it would require regenerating `chia_v01.sqlite`, a
  full analytical re-run and re-validation, updating this document, and
  re-baselining the seven database-hash anchors — a dedicated slice, not covered
  here.
