# Version 0.1.0 — Project Foundation

**Date:** August 28, 2026

## Project Established

The Community Health Intelligence Atlas (CHIA) project was created to explore geographic patterns of health burden across the United States using authoritative public datasets.

The project began after reviewing CDC research showing that chronic diseases frequently cluster geographically and are closely associated with socioeconomic and healthcare-access factors. Rather than focusing on a single disease, the project's objective became understanding the combination of characteristics associated with overall community health burden.

---

## Major Decisions

### Project Scope

Version 1 will focus exclusively on the United States.

The initial geographic unit of analysis will be counties, with the potential to incorporate ZIP Code Tabulation Areas or census tracts in future versions if doing so materially improves the analysis.

---

### Project Purpose

CHIA is a research and decision-support tool.

It is **not** intended to diagnose individuals, predict personal health outcomes, or provide medical advice.

---

### Development Philosophy

The project will emphasize:

* transparency
* reproducibility
* explainable methods
* maintainability
* practical usefulness

Complexity will only be added when it produces meaningful analytical value.

---

### Technical Direction

Version 1 will remain fully offline after data acquisition.

The finished deliverables should require no server infrastructure, cloud hosting, user accounts, or ongoing maintenance.

---

## Initial Deliverables

The following foundational documents have been created:

* Executive Report (Foundation)
* Methodology
* Data Dictionary
* Project Principles
* Project Log

Additional foundational documents will be added before implementation begins.

---

## Project Vision

The long-term vision is an interactive research atlas that helps answer questions such as:

* Which communities experience the greatest overall health burden?
* Which characteristics consistently accompany high health burden?
* Which communities demonstrate unusual resilience despite socioeconomic disadvantage?
* Which communities may benefit most from targeted interventions?

The atlas is intended to provide insight rather than definitive explanations.

---

## Version 1 Success Criteria

Version 1 will be considered complete when it includes:

* A documented methodology
* A transparent Health Burden Index
* County-level rankings
* Community comparison capability
* Similar county identification
* A downloadable Excel workbook
* A static offline HTML atlas
* Supporting documentation
* A complete data dictionary

No additional features are required for Version 1.

---

## Lessons Learned

The project's original concept centered on identifying the "sickest places in America."

Early research demonstrated that a more valuable objective is understanding the combinations of health, community, and healthcare characteristics that consistently occur together.

This shift transformed CHIA from a simple ranking exercise into a broader community health intelligence framework.

# Version 0.2.0 — County Explorer v0.2 UX: Data Vintage & Source Refresh Foundation (CE-E12A)

**Date:** September 5, 2026

## Scope

Architecture / design only, documentation-only. Establishes authoritative source-vintage metadata for the CHIA v0.1 analytical sources so the governing principle holds explicitly: *a CHIA profile must always be reproducible from a known set of source-data vintages and a known methodology version.* CE-E12A records the design, the exact target values, and the migration plan; it changes no `.py`, `.sql`, `.sqlite`, frontend, or test file. Persisting the metadata into the database is the separately authorized follow-on slice CE-E12B.

## Deliverables

- `Documentation/ANALYTICAL_DATA_SOURCES.md.txt` (new) — the authoritative analytical-source catalogue (counterpart to `GEOGRAPHIC_DATA_SOURCES.md.txt`): per source — publisher, dataset, vintage, canonical URL, retrieved date, raw + processed artifact paths, and reproducible SHA-256 / md5 for every build-input workbook and its upstream HRSA export; the `reference_period` string convention; and the current-vs-target state of the persisted `source` table.
- `Documentation/CE_E12A_Data_Vintage_Design.md.txt` (new) — the design record: the seven determinations, the reproducibility contract, the CE-E12B migration + seven-anchor hash re-baseline checklist, and six open decisions (Q-D1–Q-D6) with recommended dispositions.
- This CE-E12A entry.

## Key determinations

- **`county_period.period` is not repurposed.** It is the analytical-run partition key, coupled 1:1 to `methodology_version` (`v0.1`) and asserted `== 'v0.1'` by `validate_v01_county_explorer.py` and the backend suite. “Data vintage” becomes a new derived presentational concept built from per-source `reference_period`.
- **Source vintage.** All four v0.1 sources are one HRSA Data Warehouse snapshot; every raw record carries a uniform `Data Warehouse Record Create Date` of 2026-08-29 (verified across all rows: PC 79,358 / DH 46,316 / MH 40,736 / MUA-P 19,778). Target `reference_period` for every `source` row: `HRSA Data Warehouse snapshot 2026-08-29`, with `url` and `accessed_at` populated (both `NULL` today; placeholder `v0.1 source period` today).
- **Reproducibility metadata.** Minimum per-source set adds an artifact **SHA-256** (and optionally the build-input filename). These need one or two additive nullable `TEXT` columns on `source` — the only schema change, and it is deferred to CE-E12B because it necessarily rewrites the byte-pinned database.
- **No analytical value can change.** No analytical script (`normalize_v01_database.py`, `build_v01_dimension_scores.py`, `build_v01_composite_scores.py`, any `validate_v01_*`) reads the `source` table; it is consumed only by the presentation provenance join and the CE-E11 CSV. CE-E12B will additionally enforce a before/after equality check on `normalized_measure` / `dimension_score` / `composite_score`.

## Database re-baseline constraint (informs CE-E12B, not touched here)

`Data/Model/chia_v01.sqlite` sha-256 `0d8bb417ccf72acf0cef7d17bcca15627900d0df419fc259de553a95b9aa2966` is pinned by six backend test files (`test_ce_a06`, `test_ce_b01`, `test_ce_b02`, `test_ce_d01_concurrent_connection`, `test_ce_d01_county_reference_correction`, `test_ce_e09`); md5 `f53b3de17b627b3b02796df9de33b5a4` is the gate value. Any database change is a coordinated update of all seven anchors — the defining work of CE-E12B.
